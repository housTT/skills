`tt-project`:

- after_push of an ordinary push gets TTP_PUSHED_VERSION (version_bump's version at the pushed commit); a malformed (scalar) after_push is recorded as a failure that alerts, never a quiet skip, and does not count as off; a newer ok receipt clears an after_push_failed alert an older receipt raised in the same tick; malformed after_push test picks the latest receipt by start time (ids from the same second sort by sha)
- ttp config inside a run (TTP_RUN_ID or TTP_RUN_DIR set) refuses to change a user-only setting (coordinator.NEEDS_USER), directly, through a parent key or account-wide; reading, other keys and turning a SAFE_WHEN_OFF switch off still work
- document the command watcher's exit codes and "error": true (exit 0 or 1 is a normal run whose lines are reports; only the JSON boolean marks the watcher's own error), with tests for both, a sweep before the schedule exists, and an old database with open watcher issues that migrates and then recovers; ttp doctor --scheduler checks the installed runtime's command-watcher lifecycle (reports at exit 1, an "error": true line repaired and reopening, a clean run closing all) in a scratch project, each tick in a fresh process, with no model and no spend; the scheduler check writes its scratch schedule with write_json and exempts its scratch watcher output from the durable-write rule
- a queued wait whose note names an ask or task is refreshed once that ask resolves or that task is done: note rewritten, cached probe verdicts dropped and its probe rerun at once (a probe-less wait runs now); retry_when, dependencies, start_when/start_after, planned windows and attempts stay; once per wait and evidence; rename the ref-wait test helper so it no longer shadows the shared _ask helper; ref-wait evidence never wakes a probe-less wait: it only refreshes the note (and drops/reruns a wait's own model-free probe), so stale evidence cannot wake a task after every hand-off; known gap documented
- a task labelled both rebases:<branch> and continues:<review> starts its worktree from the rebased branch's head, not the reviewed head
- the daemon captures a runtime identity receipt at startup (version, SOURCE_COMMIT, runtime path, pid, process start, boot, instance, provenance) and records its last completed tick apart from the heartbeat; heartbeat, start marker, health, /api/state, overview and ttp status show it, with 'restart pending' when the files differ and 'unverified' for a daemon without one; the tick_done file is written with durable_write
- a stuck finish task cannot block a host-side upgrade: takeover with a fenced generation, one upstream escalation after 6 h, sooner merge retry; document the finish-lock takeover and the sooner host-side merge retry
