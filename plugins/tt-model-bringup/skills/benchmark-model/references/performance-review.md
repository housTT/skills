# Performance review before benchmarks and evaluations

Use this review in optimized-vLLM and before the full benchmark/eval pass. A working API or scorer is insufficient evidence that the evaluation path is efficient.

## Establish expectations and a serving reference

Read earlier decoder/full-model, post-datatype-selection token-out and Stage 10 measurements. Derive expected warmed TTFT and decode tokens/s/user (t/s/u, `1000 / mean_tpot_ms`) for the planned prompt/output lengths, precision, mesh and active users. Distinguish teacher-forcing/device-only numbers from token-out and serving measurements. Include all prefill chunks, sampling, token feedback and host work. Do not compare 128-token TTFT directly with 4096-token TTFT or scale it blindly: use measured prefill lengths/chunks or a documented work-based estimate. Record the measurement sources, expected ranges and tolerances before seeing the new results.

Inspect the current [TT Inference Server model catalogue](https://github.com/tenstorrent/tt-inference-server/tree/main/docs/model_support/llm) and [workflow guide](https://github.com/tenstorrent/tt-inference-server/blob/main/docs/workflows_user_guide.md). Choose a supported model with comparable architecture, parameter size and hardware; Qwen3-8B is an example when those properties match. Resolve the exact model/spec rather than guessing from a shorthand such as “qwen 3.8”. Read its benchmark/eval configuration and adapter or generator paths. Reuse relevant request pooling, batching, chunked-prefill, trace/cache, sampling and metric collection patterns. Record source links/commit and differences in precision, context, thinking mode and topology. Reference results are context, not transplanted acceptance thresholds; do not switch implementations to obtain the reference model's results.

## Pilot, diagnose and improve

Warm the serving configurations for 1, 8 and 16 users, with each configuration's matching trace and cache buckets. Run a small repeated performance pilot and representative eval requests, including normal prompt lengths, long reasoning outputs, mixed lengths and a partial batch. Compare actual TTFT and t/s/u against the expected range. Record both absolute differences and ratios, plus aggregate useful output tokens/s and real-request wall time. Separate cold compilation and trace capture from steady-state latency, and queueing from execution.

When results fall outside expectations, investigate before starting the full pass. Locate the time in tokenization/template preparation, HTTP/client serialization, request admission, scheduler gaps, sequential prefill/chunk sizing, trace recapture/cache misses, dispatch, communication, sampling/readback/token feedback, response streaming or CPU scoring. Use serving benchmark JSON, host phase timings and existing non-serving profiles; keep the live-server device-profiler prohibition. Fix avoidable overhead, use $autofix where appropriate, and repeat the identical pilot after each change. Preserve correctness, context and precision. If a residual gap is intrinsic, explain it with timing evidence and revise the expectation explicitly; do not silently loosen a threshold until the run passes.

Populate `performance_expectations` in the run configuration from this analysis for profiles `1`, `8` and `16`: `max_ttft_ms`, `min_decode_tokens_per_second_per_user`, and a `source` identifying measurements and the derivation. The runner measures all three profiles before accuracy and fails on an unmet expectation, retaining the measurements for diagnosis. Investigate and repair the cause, then rerun in a fresh output directory. The full report must explain remaining overhead and reference-recipe differences in `RUN_NOTES.md`.

## Evaluation parallelism and batch buckets

Compare N identical real requests in a warmed batch-N run against the same N requests run serially at batch 1, for N = 8 and 16. Include prefill, padding, host work, scoring and the long-tail drain in the eval comparison. Report `speedup_N = serial_wall_seconds / batched_wall_seconds`; use batching only with a repeatable win. The runner's fixed-length performance comparison is an initial estimate; verify it with representative eval inputs before selecting `accuracy_concurrency`. Choose 1 if neither secondary profile helps; do not run a slow serialized evaluation merely because it produces valid scores. Estimate the full pass duration from the pilot and investigate a slower-than-predicted live pass before burning the stage budget.

Use one shared request pool for tasks with identical effective generation settings. Keep each task's scorer, question identity, thinking mode, output budget and few-shot protocol intact. Group incompatible settings separately in the same invocation; do not change protocols to combine them. Preserve outputs in original request order even when completion order differs.

Use the model’s supported physical batch buckets. Mask inactive attention, KV-cache updates, sampling and token feedback, and return only real requests. Reuse warmed traces for partial batches; never duplicate evaluation questions to fill unused rows. HTTP concurrency controls the client pool; record the actual device batch separately. Choose buckets from measured latency and memory capacity rather than imposing one model’s layout on every adapter.

Check mixed-length cache isolation, page growth, slot refill and partial-tail results against batch 1. During the full pass, track completed requests, active users, TTFT/TPOT, useful throughput and wall time. Diagnose stalls and serialization using lightweight host evidence. Keep failed-run logs and all questions in the scoring denominator. A low accuracy score remains a reportable result; an unexplained performance regression requires investigation.
